 MindNest RAG — 면접 소재 정리

> 목적: RAG + LangChain 구현 경험을 면접에서 설명하기 위한 자료  
> 기준: "잘 됐다"가 아니라 "왜 그렇게 판단했는가"를 중심으로 서술

---

## 1. 한 문장 소개

> "CBT 기반 심리 상담 앱에 RAG를 도입해 인지 왜곡 지식베이스를 구축하고, Naive RAG의 검색 품질 한계를 분석해 MultiQueryRetriever로 개선한 경험입니다."

---

## 2. 아키텍처

```
React
  ↓
Spring Boot  (세션 관리, API 키 보관)
  ↓ HTTP
FastAPI      (LangChain + ChromaDB — RAG 서버)
  ↓
Claude API
```

**왜 두 서버로 분리했나?**  
LLM 파이프라인은 Python 생태계(LangChain, ChromaDB 등)가 압도적으로 성숙해 있다.  
Spring Boot에 Python 라이브러리를 억지로 연동하는 것보다, 역할을 분리해 각 서버가 잘하는 것에 집중하는 게 맞다고 판단했다.

---

## 3. 지식베이스 설계

**청킹 전략: 인지 왜곡 유형 × 상황 카테고리 조합**

```
낙인 찍기 × 직장/성과  → labeling_work.md
낙인 찍기 × 인간관계   → labeling_relationship.md
흑백논리 × 직장/성과   → all_or_nothing_work.md
...총 16개 청크
```

**왜 고정 크기(Fixed-size) 청킹을 안 썼나?**  
심리 상담 도메인은 맥락이 중요하다. "낙인 찍기"라는 개념은 상황(직장/관계/자존감)에 따라 반례 접근법이 다르다.  
고정 크기로 자르면 왜곡 유형과 상황 맥락이 한 청크에 함께 담기지 않는다.  
→ 의미 단위 청킹이 이 도메인에 더 적합하다고 판단했다.

**데이터 한계**  
실제 상담 데이터는 개인정보·의료정보라 공개 데이터셋이 없다.  
청크 내 사용자 표현 예시는 전부 Synthetic Data (LLM으로 생성).  
→ 이 한계를 인정하고, 파이프라인으로 보완하는 전략을 선택했다.

---

## 4. 기술 선택 근거

| 기술 | 선택 이유 |
|------|---------|
| **ChromaDB** | 로컬 파일 기반, 별도 서버 불필요, 프로토타이핑에 빠름. 운영 스케일이 되면 Pinecone/Weaviate로 교체 예정 |
| **paraphrase-multilingual-MiniLM-L12-v2** | 한국어 포함 다국어 지원, FastEmbed로 ONNX 경량 추론 (torch 불필요), 무료 |
| **MultiQueryRetriever** | 데이터 한계를 검색 파이프라인으로 보완하는 접근. LangChain 내장이라 추가 설치 없음 |
| **FastAPI** | LangChain 생태계와 Python 공유, 비동기 지원, Spring Boot와 HTTP로 연동 용이 |

## 5. Before/After — 임팩트 케이스 3개

> 전체 비교: `docs/before_after_examples.md`

---

### Case A — 자격증 1점 차이 불합격 (자존감 × 흑백논리)

**입력:** "목표했던 자격증 시험에서 1점 차이로 떨어졌어. 이 정도도 못 하면 나는 뭘 해도 안 되는 사람이야."

| | Before (RAG 없음) | After (RAG 적용) |
|--|-----------------|----------------|
| counter_hints[0] | "1점은 운, 컨디션 차이일 수 있음" | **"1점 차이는 합격 근접 증거"** |
| counter_hints[1] | "과거 성공 경험들의 존재" | "재도전 시 합격 가능성" |
| counter_hints[2] | "재응시 기회와 개선 가능성" | "시험 준비 과정의 실력 축적" |

**차이점 해설:**  
Before는 "운이었을 수도" (불확실성 프레임), After는 "거의 합격했다는 증거" (강점 재프레임).  
CBT에서 흑백논리의 반례는 "이분법적 실패"를 연속선으로 되돌리는 것이다.  
After의 표현이 이 원칙에 더 정확히 맞는다.

**왜 RAG가 이 차이를 만들었나:**  
`all_or_nothing_self_esteem.md` 청크가 검색됐고, 해당 청크에 "부분 성공을 성공으로 인식" 접근법이 포함되어 있다.  
MultiQueryRetriever가 "1점 차이로 떨어졌어"를 "거의 합격했지만 실패로 인식", "완벽하지 않으면 전부 실패"로 확장해 더 정확한 청크를 검색했다.

---

### Case B — 카톡 읽씹 (인간관계 × 성급한 결론)

**입력:** "카톡 읽씹 당했어. 분명히 내가 뭔가 잘못 말했나봐. 나를 싫어하게 된 것 같아."

| | Before | After |
|--|--------|-------|
| fact | "카톡 메시지에 아직 답장이 오지 않았다" | **"카톡 메시지가 읽혔으나 답장이 오지 않았다"** |

**차이점 해설:**  
"읽씹"의 핵심은 **읽었음에도 답하지 않은 것**이다.  
Before는 단순히 "답장이 없다"로 추출해 사실 정보가 손실됐다.  
After는 "읽혔으나 답하지 않음"이라는 정확한 사실을 담았다.  
fact 추출의 정밀도가 높을수록 이후 interpretation, counter_hints 품질도 올라간다.

**왜 RAG가 이 차이를 만들었나:**  
`jumping_conclusions_relationship.md` 청크가 검색됐고, "읽씹" 상황 표현 예시가 포함되어 있다.  
이 청크가 컨텍스트에 주입되면서 LLM이 "읽씹"의 정확한 상황을 더 잘 추출했다.

---

### Case C — 발표 말 꼬임 (직장 × 낙인 찍기)

**입력:** "오늘 발표에서 말이 꼬였어. 나는 역시 안 되는 사람이야. 이런 것도 제대로 못 하다니."

| | Before | After |
|--|--------|-------|
| counter_hints[2] | "말이 꼬친 것은 준비 부족 vs 능력 문제" | **"타인도 같은 실수를 하는 보편성"** |

**차이점 해설:**  
Before의 "준비 부족 vs 능력 문제"는 원인을 추궁하는 프레임이다.  
After의 "보편성"은 CBT의 **탈중심화(Decatastrophizing)** 기법 — "이 실수는 나만 하는 게 아니다"는 관점 전환이다.  
낙인 찍기 왜곡의 핵심 반례가 "행동과 자아를 분리 + 보편성 인식"이라는 점에서 After가 더 정확하다.

## 6. RAG 효과가 미미한 이유 — 정직한 분석

> "RAG 도입 후 Before/After 비교를 했는데, 효과가 예상보다 작았습니다."

이 질문은 나올 수 밖에 없고, **이걸 명확하게 설명할 수 있는 게 실력이다.**

### 이유 1. Claude가 CBT를 이미 학습했다

Claude Sonnet/Haiku는 사전학습 데이터에 CBT 이론이 포함되어 있다.  
"낙인 찍기의 반례는 행동과 자아를 분리하는 것" 수준의 지식은 RAG 없이도 생성 가능하다.  
RAG가 효과를 내려면 "LLM이 모르는 것"을 주입해야 하는데, 현재 청크 내용이 LLM의 기존 지식과 많이 겹친다.

### 이유 2. 합성 데이터의 한계

실제 상담 데이터가 없어서 청크의 사용자 표현 예시가 전부 LLM이 생성한 것이다.  
실제 사용자는 "역시 난 또 이렇네", "어차피 안 되겠지" 같은 예측 불가한 구어체를 쓴다.  
합성 데이터로 만든 청크가 이 다양성을 완전히 커버하지 못한다.

### 이유 3. 도메인 자체 특성

심리 상담 도메인은 "정답이 하나"인 도메인이 아니다.  
동일한 인지 왜곡이라도 사람마다 맞는 반례가 다를 수 있고, CBT에서 인정하는 다양한 접근법이 모두 유효하다.  
→ Before/After가 "다른 것"이지 "하나가 틀린 것"이 아닌 경우가 많다.

## 7. 그래도 RAG를 유지하는 이유

한계를 알면서 왜 RAG를 도입했는가 — 이게 판단력을 보는 질문이다.

**① 지식베이스 교체만으로 도메인 특화 가능**  
모델 재학습 없이 청크 파일만 수정하면 CBT 지식을 업데이트할 수 있다.  
새로운 인지 왜곡 유형이나 상황을 추가하는 것이 프롬프트 수정보다 체계적이다.

**② 실제 상담 데이터 확보 시 즉시 효과 극대화**  
현재 합성 데이터의 한계는 파이프라인의 문제가 아니라 데이터의 문제다.  
실제 상담 데이터를 ingest하면 파이프라인 수정 없이 품질이 올라간다.  
현재 구조는 그 확장에 대비되어 있다.

**③ RAG 파이프라인 구축 자체가 목표의 일부**  
면접 소재로서 Naive RAG → 문제 인식 → MultiQueryRetriever 개선 과정을 직접 구현하고 비교한 경험이다.  
"효과가 극적으로 좋아졌다"보다 "왜 안 되는지 알고 어떻게 대응했는지"가 더 가치 있는 경험이다.

## 8. 예상 면접 Q&A

### 기초

**Q. RAG가 뭔가요?**  
> "Retrieval-Augmented Generation입니다. LLM을 호출하기 전에 관련 문서를 벡터 DB에서 검색해 컨텍스트로 주입하는 방식입니다. 모델 재학습 없이 도메인 지식을 주입할 수 있어서, 지식이 자주 바뀌거나 비공개 데이터를 다룰 때 유리합니다."

**Q. 왜 Fine-tuning 대신 RAG를 선택했나요?**  
> "세 가지 이유입니다. 첫째, CBT 지식이 업데이트될 때 모델 재학습 없이 지식베이스만 교체하면 됩니다. 둘째, 실제 상담 데이터가 개인정보라 Fine-tuning 데이터셋 구축이 불가능합니다. 셋째, RAG는 검색된 청크가 근거로 남아서 LLM 답변이 어디서 왔는지 추적이 가능합니다."

**Q. 임베딩이 뭔가요?**  
> "텍스트를 수백 차원의 벡터로 변환하는 것입니다. 의미가 비슷한 문장은 벡터 공간에서 가까운 위치에 놓입니다. 저는 `paraphrase-multilingual-MiniLM-L12-v2` 모델을 사용했는데, 한국어를 포함한 다국어를 지원하고 FastEmbed로 ONNX 경량 추론이 가능해서 선택했습니다."

**Q. 청킹 전략을 어떻게 결정했나요?**  
> "고정 크기 대신 의미 단위로 청킹했습니다. 인지 왜곡 유형과 상황 카테고리를 조합해 16개 청크를 만들었습니다. 심리 상담 도메인은 '낙인 찍기'라도 직장 상황과 인간관계 상황에서 반례 접근법이 다르기 때문에, 맥락이 한 청크에 함께 담겨야 한다고 판단했습니다."

---

### 설계 판단

**Q. Before/After 비교에서 RAG 효과가 미미했다고 하셨는데, 그럼 RAG가 필요 없는 거 아닌가요?**  
> "날카로운 질문입니다. 효과가 작은 이유를 분석해보니 두 가지였습니다. 첫째, Claude가 CBT를 이미 학습해서 RAG 없이도 기본 답변이 가능합니다. 둘째, 합성 데이터로 만든 청크라 실제 사용자 표현 다양성을 완전히 커버하지 못합니다. 다만, 실제 상담 데이터를 확보하면 같은 파이프라인으로 효과가 훨씬 커집니다. 또 Fine-tuning과 달리 지식 업데이트가 쉽다는 구조적 장점이 있어서 유지 판단을 했습니다."

**Q. MultiQueryRetriever를 왜 도입했나요?**  
> "사용자 입력이 구어체라서 청크 표현과 어휘가 달라지면 관련 청크가 검색 안 되는 문제가 있었습니다. 예를 들어 사용자가 '또 망했어'라고 하면 청크의 '나는 실패자다' 표현과 벡터 유사도가 낮게 나옵니다. MultiQueryRetriever는 LLM이 쿼리를 3개 다른 표현으로 확장한 뒤 각각 검색하고 중복을 제거합니다. 기본 프롬프트가 영어라 한국어 CBT 도메인에 맞게 커스터마이징했습니다."

**Q. 응답 지연이 생기지 않나요?**  
> "MultiQueryRetriever는 검색 전에 LLM을 한 번 더 호출합니다. 이를 위해 가장 저렴하고 빠른 claude-haiku를 사용하고, temperature를 0.3으로 낮춰 일관된 쿼리 변형이 나오도록 했습니다. 또 MultiQueryRetriever 호출이 실패하면 단순 벡터 검색으로 자동 폴백하도록 예외 처리했습니다."

---

### 심화

**Q. Hybrid Search는 알고 있나요?**  
> "BM25 키워드 검색과 벡터 검색을 EnsembleRetriever로 합산하는 방식입니다. 의미 검색이 실패할 때 키워드로 보완할 수 있습니다. 이번 프로젝트에서 도입을 검토했는데, 한국어 BM25는 형태소 분석기(kiwipiepy) 없이 공백 분리만으로는 품질이 낮고, 현재 청크가 16개라 키워드 검색의 실익이 크지 않다고 판단해 보류했습니다. 청크 수가 수백 개 이상으로 늘어나면 도입할 기법입니다."

**Q. Reranking은요?**  
> "k를 크게 잡아 넓게 검색한 뒤 Cross-encoder로 재순위를 매겨 상위 k개를 반환하는 방식입니다. Naive RAG의 '정밀도 낮은 검색' 문제를 해결하는 현업 검증 패턴입니다. 다만 현재 ChromaDB에 벡터가 63개뿐이라, k=10으로 넓게 잡으면 전체의 16%를 검색하게 되어 Reranker의 작동 조건이 충족되지 않습니다. 데이터 규모가 커지면 도입 가치가 생깁니다."

**Q. 환각(Hallucination)은 어떻게 방지했나요?**  
> "두 가지로 접근했습니다. 첫째, 프롬프트에 'JSON 외 텍스트는 절대 포함하지 마세요', '진단명·처방·약물 관련 표현 금지' 제약을 명시했습니다. 둘째, RAG로 주입된 청크가 LLM의 답변 근거가 되어, 완전히 허구의 내용보다는 청크에 기반한 답변이 나올 가능성이 높아집니다. 다만 RAG가 환각을 완전히 제거하지는 않으며, 운영 단계에서는 출력 검증 레이어를 추가해야 한다고 생각합니다."
