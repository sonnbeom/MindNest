## 1. RAG가 뭔가요?

**RAG = Retrieval-Augmented Generation**  
직역하면 "검색으로 보강된 생성"입니다.

### 문제: LLM은 일반 지식은 잘 알지만 내 프로젝트 지식은 모른다

ChatGPT나 Claude에게 "낙인 찍기 왜곡에 대한 CBT 반례를 줘"라고 물으면 일반적인 답을 줍니다.  
하지만 MindNest 특유의 상황별 반례, 우리가 직접 정리한 케이스북은 모릅니다.

### 해결책: 답을 생성하기 전에 관련 자료를 먼저 찾아서 LLM에게 준다

```
[기존 방식]
사용자 입력 → LLM → 답변 (LLM 머릿속 지식만 사용)

[RAG 방식]
사용자 입력 → 지식 베이스에서 관련 자료 검색 → LLM에게 입력 + 자료 함께 전달 → 더 정확한 답변
```

### 쉬운 비유

오픈북 시험 vs 클로즈드북 시험.  
RAG는 LLM한테 "시험 보기 전에 교과서 관련 페이지를 찾아서 읽게 해주는 것"입니다.  
LLM이 틀린 말을 할 확률이 줄고, 우리 도메인에 맞는 답을 할 확률이 높아집니다.

## 2. 임베딩 — 텍스트를 숫자로 바꾸는 것

### 왜 텍스트를 숫자로 바꾸나요?

컴퓨터는 "나는 실패자야"와 "나는 무능한 사람이다"가 비슷한 말이라는 걸 글자만 봐서는 모릅니다.  
하지만 두 문장을 수백 개의 숫자 배열(벡터)로 변환하면, 의미가 비슷한 문장은 숫자 배열도 비슷해집니다.

```
"나는 실패자야"       → [0.12, 0.87, 0.34, 0.56, ...]  (수백 개 숫자)
"나는 무능한 사람이다" → [0.11, 0.85, 0.36, 0.54, ...]  (비슷한 숫자들)
"오늘 날씨가 좋다"    → [0.92, 0.03, 0.71, 0.12, ...]  (전혀 다른 숫자들)
```

이 숫자 배열을 **벡터(vector)** 라고 하고, 텍스트를 벡터로 바꾸는 과정을 **임베딩(embedding)** 이라고 합니다.

### 비유

임베딩은 텍스트를 지도 위의 좌표로 바꾸는 것과 같습니다.  
의미가 비슷한 문장들은 지도 위에서 가까운 곳에 위치하게 됩니다.  
검색할 때는 "사용자 입력과 가장 가까운 좌표에 있는 자료"를 찾으면 됩니다.

## 3. 벡터 DB — 숫자로 바꾼 텍스트를 저장하는 창고

### 일반 DB와 뭐가 다른가요?

일반 DB (MySQL 등): `WHERE content = '실패자'` — 정확히 그 단어가 있는 것만 찾음  
벡터 DB: "이 숫자 배열과 가장 비슷한 배열을 가진 문서를 찾아줘" — **의미로 검색**

| 일반 DB 검색 | 벡터 DB 검색 |
|-------------|-------------|
| 키워드가 정확히 일치해야 함 | 의미가 비슷하면 검색됨 |
| "나는 실패자야" 검색 시 "실패자" 포함 문서만 나옴 | "나는 쓸모없어"로 검색해도 "낙인 찍기" 청크가 나옴 |

### MindNest에서 사용하는 벡터 DB: ChromaDB

- 로컬에서 파일 형태로 저장 (`chroma_db/chroma.sqlite3`)
- 설치와 설정이 간단해 프로토타이핑에 적합
- 실제 서비스 규모가 커지면 Pinecone, Weaviate 등 클라우드 DB로 교체 가능

## 4. 청크 — 무엇을 저장하는가

### 청크(Chunk)란?

지식 베이스를 통째로 LLM에게 줄 수는 없습니다. LLM이 한 번에 처리할 수 있는 텍스트 양(컨텍스트 윈도우)에 한계가 있기 때문입니다.  
그래서 지식을 작은 조각으로 나눠서 저장합니다. 이 조각 하나하나를 **청크**라고 합니다.

### MindNest의 청크 설계 전략: "의미 단위 청크"

많은 RAG 시스템이 문서를 무작정 500자씩 잘라서 청크를 만듭니다 (고정 사이즈 분할).  
MindNest는 다른 전략을 선택했습니다.

```
파일 1개 = 인지 왜곡 유형 1개 × 상황 카테고리 1개
```

예시:
```
labeling_work.md           → 낙인 찍기 × 직장/성과 상황
labeling_self_esteem.md    → 낙인 찍기 × 자존감 상황
all_or_nothing_work.md     → 흑백논리 × 직장/성과 상황
jumping_conclusions_relationship.md → 성급한 결론 × 인간관계 상황
```

### 청크 내부 구조

각 파일 안에는 이런 내용이 들어있습니다:

```markdown
# 낙인 찍기 — 직장/성과 상황

## 왜곡 유형
낙인 찍기 (Labeling) — 실수 하나를 자아 전체로 확대

## 상황 카테고리
직장/성과

## 관련 사용자 표현 예시
- "나는 무능한 사람이다"
- "나는 실패자야"
- "발표 망쳤어, 나는 역시 안 되는 사람이야"

## 핵심 패턴
"실수했다" 대신 "나는 실패자다"로 비약

## 반례 접근법
- 실수와 실패자는 다름 — 행동과 자아를 분리
- 과거에 성공적으로 해낸 업무 경험 탐색
```

### 왜 이렇게 만들었나요?

**검색 정확도** 때문입니다.

사용자가 "나는 발표 망쳤어, 나는 역시 안 되는 사람이야"를 입력하면:

- 이 문장의 벡터가 `labeling_work.md`의 "관련 사용자 표현 예시" 벡터와 **가장 유사**합니다
- 그러면 `labeling_work.md` 전체가 검색 결과로 나옵니다
- LLM은 이 청크 안의 반례 접근법까지 함께 받아서 더 정확한 답을 생성합니다

고정 사이즈로 잘랐다면? "관련 사용자 표현 예시" 섹션과 "반례 접근법" 섹션이 다른 청크로 잘릴 수 있습니다. 그러면 반례 없이 왜곡 유형만 검색되는 일이 생깁니다.

## 5. 청크 사이즈 — 얼마나 잘게 자르는가

### 코드 설정

```python
splitter = MarkdownTextSplitter(chunk_size=500, chunk_overlap=50)
```

- `chunk_size=500`: 하나의 청크가 최대 500자
- `chunk_overlap=50`: 청크를 자를 때 앞 청크의 끝 50자를 다음 청크의 시작에 중복 포함

### overlap이 왜 필요한가요?

문서를 딱 잘라 나누면 맥락이 끊길 수 있습니다.

```
[청크 A 끝부분] ...실수와 실패자는 다름 — 행동과 자아를
[청크 B 시작부분] 분리해서 생각하는 게 핵심입니다...
```

overlap 50자가 있으면:
```
[청크 A 끝부분] ...실수와 실패자는 다름 — 행동과 자아를
[청크 B 시작부분] 실수와 실패자는 다름 — 행동과 자아를 분리해서 생각하는 게 핵심입니다...
```

→ 문장이 잘리더라도 의미가 이어집니다.

### 실제로는 어떻게 됐나요?

MindNest의 청크 파일들은 이미 400자 내외로 작게 설계되어 있습니다.  
그래서 실제로는 `chunk_size=500` 기준에 걸리지 않아 파일 1개 = 청크 1개 그대로 저장됩니다.  
**splitter는 안전망 역할**을 하는 셈입니다 (파일이 커지더라도 500자 이상 넘어가면 자동으로 분할).

## 6. 검색 — 어떻게 찾는가 (k=3)

### 검색 흐름

```
1. 사용자 입력 텍스트를 벡터로 변환 (임베딩)
2. ChromaDB에서 코사인 유사도를 계산해 가장 유사한 청크 k개 반환
3. 반환된 청크를 LLM 프롬프트에 주입
```

### 코사인 유사도란?

두 벡터가 얼마나 같은 방향을 가리키는지 측정하는 수치입니다 (0~1, 1에 가까울수록 유사).

비유: 두 사람이 같은 방향을 바라보면 유사도가 높고, 등을 맞대고 반대를 보면 유사도가 낮습니다.

### k=3의 의미

```python
retrieval_k: int = 3
```

검색 시 가장 유사한 청크를 **3개** 가져옵니다.

- k=1: 가장 비슷한 것 1개만 → 정보가 부족할 수 있음
- k=3: 상위 3개 → 다양한 관점의 반례를 LLM에게 제공
- k=10: 너무 많음 → 관련 없는 정보가 섞여 오히려 LLM을 혼란시킬 수 있음

## 7. LangChain 파이프라인 — 전체 흐름

### LangChain이 뭔가요?

LLM 앱을 만들기 위한 Python 라이브러리입니다.  
LLM 호출, 프롬프트 구성, RAG 파이프라인 연결 등을 쉽게 조합할 수 있습니다.  
"LLM 작업을 레고 블록처럼 조립하는 도구"라고 생각하시면 됩니다.

### LCEL (LangChain Expression Language)

LangChain에서 파이프라인을 `|` 기호로 연결하는 문법입니다.

```python
chain = (
    RAG로_프롬프트_보강
    | 프롬프트_템플릿
    | LLM
    | 출력_파서
)
```

마치 Unix 파이프처럼 앞 단계의 출력이 다음 단계의 입력이 됩니다.

### MindNest 호출 1 (intake_analysis) 파이프라인

```
사용자 입력 텍스트
    ↓
ChromaDB에서 관련 청크 3개 검색
    ↓
시스템 프롬프트 끝에 청크 내용 추가
    (예: "[관련 인지 왜곡 지식] 낙인 찍기 × 직장 상황...")
    ↓
Claude API 호출
    ↓
JSON 응답 파싱
    (thoughts, fact, interpretation, counter_hints, current_actions)
```

### MindNest 호출 2 (reframe_generation) 파이프라인

```
선택한 생각 + 사실 텍스트
    ↓
ChromaDB에서 재구성 예시 청크 검색
    ↓
시스템 프롬프트에 재구성 예시 추가
    ↓
Claude API 호출
    ↓
재구성 문장 텍스트 반환
```

## 8. 임베딩 모델 선택 이유

### 선택한 모델

`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`

### 선택 기준

| 기준 | 내용 |
|------|------|
| 한국어 지원 | 다국어(multilingual) 모델이라 한국어 문장도 의미 있는 벡터로 변환 가능 |
| 설치 경량 | FastEmbed (ONNX 기반)으로 실행 → PyTorch 설치 불필요 → 빠른 설정 |
| 로컬 실행 | 외부 API 호출 없이 로컬에서 임베딩 처리 → 비용 없음, 인터넷 불필요 |
| 크기 | 모델 크기가 작아 메모리 부담이 적음 |

### 대안과 비교

| 모델 | 장점 | 단점 |
|------|------|------|
| **paraphrase-multilingual-MiniLM-L12-v2** (현재) | 경량, 한국어 지원, 무료 | OpenAI 모델 대비 품질 낮음 |
| OpenAI text-embedding-3-small | 높은 품질 | API 비용 발생, 외부 의존성 |
| klue/roberta | 한국어 특화 고품질 | 설치 무거움 (PyTorch 필요) |

## 9. 현재 전략의 약점과 개선 계획

### 현재 약점

#### 1. 검색 품질을 실제로 측정한 적 없다

k=3이 최적인지, 임베딩 모델이 적합한지, 청크 구조가 잘 잡히는지 — 실제 데이터로 검증하지 않았습니다.  
Before/After 비교(Phase 4)가 끝나야 "이 전략이 실제로 효과 있다"고 말할 수 있습니다.

#### 2. Naive RAG만 구현되어 있다

현재 방식은 "그냥 검색해서 프롬프트에 붙여주는" 가장 기본적인 RAG입니다.  
더 발전된 방식들이 있습니다:

| 기법 | 설명 | 현재 적용 여부 |
|------|------|--------------|
| Naive RAG | 검색 → 주입 | ✅ 적용 중 |
| Reranking | 검색된 k개를 한 번 더 정렬해 품질 향상 | ❌ 미적용 |
| Hybrid Search | 키워드 검색 + 벡터 검색 결합 | ❌ 미적용 |
| Query Expansion | 사용자 쿼리를 LLM이 먼저 확장 후 검색 | ❌ 미적용 |

#### 3. 코드 주석과 실제 모델이 불일치

`retriever.py` 주석에 `multilingual-e5-small`이라고 써있지만  
실제로 `config.py`에서 로드하는 모델은 `paraphrase-multilingual-MiniLM-L12-v2`입니다.  
→ 주석 정리 필요

### 개선 계획 (Phase 4~5에서 진행)

1. 대표 입력 10개로 Before/After 비교 실행 → 검색 품질 실측
2. k 값 튜닝 (3이 최적인지 2나 4와 비교)
3. 면접 소재로 쓸 수 있는 "개선 전/후 임팩트 있는 예시 3개" 정리

## 전체 구조 한 눈에 보기

```
[사용자 입력]
     │
     ▼
[FastAPI RAG 서버] ──────────────────────────────┐
     │                                           │
     │ 1. 입력 텍스트 임베딩                       │
     │    (paraphrase-multilingual-MiniLM-L12-v2) │
     │                                           │
     │ 2. ChromaDB 코사인 유사도 검색 (k=3)        │
     │    → 관련 청크 3개 반환                     │
     │    (예: labeling_work.md 내용)              │
     │                                           │
     │ 3. 시스템 프롬프트 + 청크 결합               │
     │                                           │
     │ 4. Claude API 호출                         │
     │                                           │
     ▼                                           │
[응답 JSON 반환 → Spring Boot → React 프론트엔드]  │
                                                 │
         지식 베이스 (data/chunks/*.md 16개 파일) ─┘
         인지 왜곡 유형 × 상황 카테고리 조합
```
